# DrivX

Premium Indian mobility: a **verified professional driver comes to you and drives your own car**.
Cab booking is modelled in the schema but disabled at launch, until licensing, insurance and
aggregator rules have been cleared.

This repository is **Phase 1** of the six-phase build plan: design system, project setup,
Firebase authentication, the data model, and security rules. Everything that is not finished is
described as unfinished below — no screen or endpoint returns a simulated success.

---

## What runs today

The emulator suite runs locally, so the rows marked **Verified** below were actually executed
against it — rules, indexes and the auth trigger included. Both front ends have now been **seen in a
browser**: the customer app through `npm run mobile:web` (Metro on `:8081`) with the emulator wired
up, signed in as two different seeded numbers through the real OTP screen — that first render found
six defects, all fixed and listed in [docs/operations.md](docs/operations.md#9-known-limitations-of-this-repository-right-now) —
and the operations console at `:3001`, whose status badges are how a stale-CSS problem was caught.
Its `/verification` screen has since become the way a driver is actually approved: it was used to
clear a real new driver through the whole onboarding chain described below, and its `/dues` screen is
where the office records the money — the ₹315 onboarding fee and one commission charge per
completed trip, at the cut the office has configured (13% unless `appConfig/commission` says
otherwise) — against a typed receipt reference.
The whole interface now runs on one **Emerald Slate** design system, documented with its measured
contrast in [docs/design-system.md](docs/design-system.md). Nothing has been drawn on a phone or
tablet yet. Each row says exactly how far it got.

### The emulator needs Java 21

`firebase emulators:start` runs the Firestore/RTDB/Storage rule engines on the JVM, and
firebase-tools 15 refuses anything below **Java 21**. `npm run emulators` locates a suitable JDK
itself (`scripts/emulators.sh` checks `JAVA_HOME`, the Homebrew kegs and `brew --prefix`), so
installing one is the only prerequisite:

```bash
brew install openjdk@21
```

Running the suite also compiles `@drivx/domain` and the functions bundle first, because the
Functions emulator loads `functions/lib/index.js` rather than the TypeScript source.

Cross-cutting decisions worth knowing before you edit:

- Shared packages are consumed as **TypeScript source** (`tsconfig.base.json` paths +
  `transpilePackages` in `next.config.ts`), so nothing builds against a stale bundle.
  `@drivx/domain` additionally emits CommonJS to `dist/` for Cloud Functions.
- Money is integer **paise** (`MoneyPaise`), formatted with `Intl` `en-IN`. Never a float.
- Time is `*Ms` epoch numbers in the domain and native Firestore `Timestamp` in the database,
  converted at the persistence boundary (`packages/firebase-client/src/serialize.ts`).
- Roles come **only** from custom claims minted by Cloud Functions. A `role` field on a profile
  document is a mirror for reporting, never an authorization input.

## Non-negotiable guardrails

These are the spec constraints the code is arranged to enforce; break them and the review fails.

1. **No fake success.** Dispatch and trip calls validate and authorize, then throw
   `not-implemented` naming their phase. A Cashfree order is only ever created for the amount the
   driver's due ledger already holds, and a due is only marked `paid` after the webhook verifies
   Cashfree's signature and re-reads the order from their API — an order that was never paid is
   never reported as settled. Without `CASHFREE_APP_ID` and `CASHFREE_SECRET_KEY` both paths refuse
   with `unavailable`/`503` instead of pretending.
   `createBooking` is the exception because it is finished: it measures the route and prices the
   fare itself, so the price a customer confirms is the price the server wrote.
2. **Client input is untrusted** for fares, roles, trip state, payment results and driver
   eligibility. Those fields are `if false` in the rules and are written only by the Admin SDK.
3. **Service-account credentials, payment secrets and Maps server keys never reach the mobile
   bundle.** They live in `functions/.env` (or Secret Manager) and the admin server only.
4. **GPS proximity alone never starts a trip.** Arrival detection requires an accuracy-qualified
   fix plus consecutive samples, and the trip still needs an OTP.
5. **Precise location is scoped to trip participants** — the assigned driver, the booking
   customer, users explicitly shared in, and staff. There is no path where every user can see
   every driver.
6. **Trip events are append-only.** No client write, no update, no delete, in any collection.
7. **Driver documents are private.** Private Storage path, private metadata document, readable
   only by the owning driver and staff.
